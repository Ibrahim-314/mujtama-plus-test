## Behaviour
- Requests are recorded from a first `request` listener: a counter `{method, route pattern, status class}` and a latency histogram. Streams/SSE and `/metrics` are excluded from latency.
  Every 60 s each instance upserts one `ops_rollups` row (requests, 5xx, slow, sum, p95, queue backlog). Timers stop with `ctx.scheduler.stop()`, so `close()` needs no change.
- Leased scheduler jobs: `ops.checks` (component checks every minute → hourly uptime tallies), `ops.alerts` (rules every minute), `ops.prune` (rollups 35 d, checks 95 d).
- Default alert rules: 5xx rate >5 % over 5 min (critical), p95 >1500 ms over 10 min, queue backlog >500, failed jobs >20 over 15 min. Metrics available: `error_rate`, `latency_p95`, `queue_backlog`, `jobs_failed`, `client_errors`.
  An alert pages once when it fires and once when it resolves. In-app channel: `notify(adminId, "ops_alert", {ref: ruleId})`. Optional: add `ops_alert` to `notify-lib.js` for Arabic wording (otherwise the generic text shows).
- SLOs: availability 99.5 %/30 d (non-5xx) and latency 95 % < 800 ms/30 d, with error budget remaining and 1 h/6 h burn rates. Exported as `mujtama_slo_error_budget_remaining_ratio`.
- `/status`: server-rendered Arabic HTML with no JS, refreshing every 60 s. Shows 6 components (email and Pi show «غير مفعّل بعد» until configured), 90-day bars, and incidents from the last 14 days. JSON is at `GET /api/status/public`.
  Note: the SPA's `#/status` (admin system status in security-ui.js) is a different, hash route.
- Product metrics (`GET /api/admin/ops/product?days=7|30|90`, cached 5 min): signups and cumulative users, DAU/WAU/MAU, stickiness, daily posts/comments/reactions, and 8 weekly retention cohorts.
  Activity = posts, comments, reactions and analytics_events. Nothing new is tracked.

## DR drill (local only, never production)
```sh
BACKUP_PASSPHRASE_FILE=pass.txt DATABASE_URL=… node server/scripts/dr-drill.js backup --out ./backups      # read-only SELECTs → mujtama-<ts>.mpb.enc + .sha256 (AES-256-GCM, scrypt)
BACKUP_PASSPHRASE_FILE=pass.txt node server/scripts/dr-drill.js drill --file ./backups/… [--scratch postgres://…/mujtama_drill_scratch] [--report-url https://…/api/ops/dr-drills]
```
The default scratch is a temporary SQLite file. A PostgreSQL scratch must have `scratch|drill|restore|test` in its database name and must not
be the source or `DATABASE_URL`. Its `public` schema is wiped before and after the drill. The drill checks the sha256, decrypts, runs the
migrations, restores rows in foreign-key order, and compares every table's count and the migration ids. Exit code 1 means the drill failed.
pg_dump backups (`*.dump.enc`) still use `ops/backup/restore-test.sh`, which needs PostgreSQL client tools that this sandbox does not have.

## UI
On `#/admin`, admins get a «📈 التشغيل والمراقبة» card. `#/admin/ops` shows KPIs, component chips, 4 inline-SVG charts (requests, error %,
p95, backlog; 1 h/6 h/24 h/7 d), an SLO table with budget bars and editable targets, alert rules (threshold and enabled), history, «تقييم
القواعد الآن»/«إرسال تنبيه تجريبي», and an incident form plus updates. It also shows DR drills and the Prometheus/tracing state.
`#/admin/ops/product` has the growth and DAU lines, signup and engagement bars, and the cohort heatmap. No chart library and no inline handlers.
