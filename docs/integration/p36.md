## What the UI team must know
- `GET /api/pi/config` is public; call it first. When `enabled:false`, hide Pi UI (every other route answers 501).
  Use `sandbox` for `Pi.init({version:"2.0", sandbox})`.
- **Responses carry a payment `status` field** (`approve`, `complete`, `cancel`, `incomplete`, receipts, wallet rows). Do not
  confuse it with the HTTP status (test helpers that spread the JSON over `{status}` will be overwritten).
- Sign-in flow: `Pi.authenticate(["username","payments"], onIncomplete)` → `POST /api/pi/auth {accessToken}`.
  `{needsLink:true, username}` → ask the user to sign in with their Mujtama+ password (or register), then
  `POST /api/pi/auth {accessToken, link:true}`. From settings while signed in, always send `link:true`.
  The legacy `POST /api/auth/pi` (auto-creates a new account from Pi) still exists if a "create account with Pi" button is wanted.
- **`onIncompletePaymentFound` fires during `Pi.authenticate`, before our session exists.** Queue the payment and call
  `POST /api/pi/payments/incomplete {payment}` after `/api/pi/auth` succeeds (route requires sign-in and a linked account).
  Result `status`: `completed` | `cancelled` | `pending` (Pi has a txid it hasn't verified yet; just inform the user, the daily
  reconciliation finishes it).
- Payment flow: `POST /api/pi/payments {amount, memo, purpose, refId?}` → pass `{amount, memo, metadata}` **exactly as returned**
  to `Pi.createPayment` (the server binds the Pi payment through `metadata.intentId`) → `onReadyForServerApproval(paymentId)` →
  `/approve` → `onReadyForServerCompletion(paymentId, txid)` → `/complete` (returns `receipt`) → `onCancel(paymentId)` →
  `/cancel {paymentId}`; if the user aborts before Pi gives a paymentId, `/cancel {intentId}`.
- Errors worth mapping: 409 `pi_not_linked` (prompt to link), 409 `pi_unverified` (retry complete in a few seconds),
  409 `pi_txid_mismatch`, 502 `pi_upstream` (Pi unreachable), 403 owner/network mismatch, 429 rate limit.
- `purpose` must be one of `tip, donation, subscription, boost, purchase, event_ticket, test` (configurable), amount ≤ 1000 by default.
- Wallet: `GET /api/pi/wallet?cursor=` (also `limit` 1–50, `status`); show `balanceNote` (we hold no balance).
  Rows with `direction:"in"` and purpose `refund` are refunds; the refunded original shows `status:"refunded"`.
- Receipt page: `GET /api/pi/receipts/:id` (intent id or paymentId); `explorerUrl` is null until there is a txid.
- Admin screen: `GET /api/admin/pi/reconciliation?date=`, `POST /api/admin/pi/reconcile {date?}`; optional refund action
  `POST /api/admin/pi/payments/:id/refund {note, txid}` (records a refund made outside the app).
