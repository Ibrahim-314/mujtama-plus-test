# العمل والفرص — Work & opportunities (Track 16)

## Phase 76 — professional profile & CV (v2.42.0)
Service: `server/services/proprofile.js` (`ctx.services.proprofile`) · migration `056_proprofile` (4 tables) · UI chunk `work-ui.js` + `work.css` · tests `server/test/proprofile.test.js`, `tests/e2e/p76.e2e.test.js`.

- `GET|PUT|DELETE /api/pro/me` — my profile (headline required; about, city, country, openTo ⊂ jobs/freelance/hiring/mentoring/volunteer, languages ≤ 8 with level, links ≤ 6 http/https, visibility public|members|followers|private, per-section visibility (only stricter), searchable, showCerts). Response includes completeness (8 checks) and the options the member may pick.
- `POST /api/pro/me/items`, `PATCH|DELETE /api/pro/me/items/:id`, `POST /api/pro/me/items/reorder {kind, ids}` — experience / education / portfolio / volunteering / award; dates `YYYY-MM` (not in the future, end ≥ start, «حتى الآن»); portfolio may point at one of the member's own published posts. ≤ 30 per kind.
- `PUT /api/pro/me/skills {skills:[{name, level 1–5, years}]}` — ≤ 30, de-duplicated by Arabic-normalised name (key reused by phase 80 endorsements).
- `GET /api/pro/u/:handle[?as=stranger|member|follower]` — viewer-filtered profile (blocked → 404, hidden → owner/staff only, locked stub when the level forbids). Verified public certificates (phase 73/70) and the mentor profile (phase 74) are linked. Member views counted once.
- `GET /cv/:handle[?download=1]` — printable Arabic RTL CV (A4 print stylesheet, no scripts), same viewer rules (cookie). PDF = the browser's «حفظ كملف PDF»; the app prints it from a hidden same-origin frame.
- `GET /api/pro/me/export` — JSON Resume v1.0.0.
- `GET /api/pro/search?q=&skill=&city=&open=&page=` — talent directory: searchable, not hidden, not flagged, adults only; visitors see public profiles, members also members-only ones.
- `POST /api/pro/u/:handle/report {reason, note}` — fake / impersonation / scam / inappropriate / other; `PRO_FLAG_REPORTS` (3) open reports take a profile out of the directory. `GET /api/admin/pro`, `POST /api/admin/pro/:handle {action: hide|restore|dismiss, reason}` — audited, notifications `pro_hidden`, `pro_restored`.
- Social profile: `GET /api/profiles/:handle` returns `pro {headline, openTo}` when the viewer may see the professional profile (link «الملف المهني» in the profile meta line).
- Minors: visibility at most followers, never listed, openTo only mentoring / volunteer.

## Phase 77 — jobs & freelance board (v2.43.0)
Service: `server/services/jobs.js` (`ctx.services.jobs`) · migration `057_jobs` (6 tables, Pi amounts BIGINT on PostgreSQL) · UI in the `work` chunk (`work-ui.js` + `work.css`) · tests `server/test/jobs.test.js`, `tests/e2e/p77.e2e.test.js`.

- `GET /api/jobs?q=&kind=&category=&mode=&city=&skill=&minPay=&sort=recent|pay&page=` — open postings (not expired, not flagged, blocked posters hidden; minors see only unpaid postings marked minors-ok). Arabic-normalised text score (title 5, skills 4, body 1); featured (Pi boost) first. Returns `options` (kinds, categories, modes, employment, pay types, report reasons, boost days/price).
- `POST /api/jobs` — `{kind: job|freelance, title ≥ 6, body ≥ 60, category, skills ≤ 10, mode remote|onsite|hybrid (+city), employment (jobs), payType fixed|hourly|monthly|none, payMin/payMax π, deadline YYYY-MM-DD, questions ≤ 3, minorsOk (unpaid only)}`. Anti-scam review: fees/deposits from applicants, off-platform contact (WhatsApp/Telegram…), recovery-phrase requests, «guaranteed income», contact details, implausible pay (`JOBS_MAX_PI`), the phase 31 fraud classifier, and new accounts (`JOBS_NEW_ACCOUNT_DAYS` = 3, unless verified) → `status: review` with reasons. Staff postings publish directly. `JOBS_MAX_OPEN` (10) active postings per member. Minors cannot post (403 `minor_restricted`).
- `GET /api/jobs/me` — my postings (with per-status counts, views, review reasons), my applications, saved postings.
- `GET /api/jobs/:id` — posting + `me {owner, canApply, why, whyCode: auth|own|not_open|expired|minor_restricted|already_applied|no_profile, application}`; views counted once per member.
- `PATCH /api/jobs/:id` (re-checked; risky edits go back to review) · `POST /api/jobs/:id/state {status: open|paused|closed|filled}` (closing/filling rejects open applications with a message) · `POST /api/jobs/:id/save {saved}` · `POST /api/jobs/:id/report {reason: scam|fee|fake|inappropriate|discrimination|other, note}` — `JOBS_FLAG_REPORTS` (3) open reports pause the posting until staff decide.
- `POST /api/jobs/:id/apply {cover ≥ 30, answers[], bid π + days (paid freelance)}` — needs a professional profile (phase 76); one application per member and posting. The employer sees the applicant's full professional profile inside the application only.
- `GET /api/jobs/:id/applications[?status=]` — employer pipeline. `GET /api/job-applications/:id` (opening it as the employer marks it `viewed`), `POST …/status {status, message}` (submitted/viewed → shortlisted → interview → offered → hired, or rejected), `PUT …/note` (private), `POST …/messages` (risky messages carry a warning for the recipient only), `POST …/withdraw`. Hiring the last open candidate of a job marks it filled.
- `POST /api/jobs/:id/boost {days: 7|14|30}` — featured listing paid in π (purpose `jobs`, `JOBS_BOOST_PI_PER_DAY` = 0.5, journal to `platform:fees`). **501 `not_configured`** with an Arabic notice while Pi payments are off (production).
- Staff: `GET /api/admin/jobs` (review queue with reasons, reports grouped by posting, totals), `POST /api/admin/jobs/:id {action: approve|remove|dismiss, reason}` — audited; removal rejects open applications with a safety message.
- Notifications: `job_app_new`, `job_app_status`, `job_app_msg`, `job_approved`, `job_removed`, `job_review`. Data map: 6 tables (boost records kept as financial records).
- UI: #/jobs (browse + filter sheet · «إعلاناتي وطلباتي»), #/jobs/new, #/job/:id (+ /edit, /applicants[?status=]), #/application/:id, #/admin/jobs. Entry points: Settings → الحساب «الوظائف والعمل الحر», buttons on #/cv and #/talent.

## Phase 78 — contracts, milestones & escrow (v2.44.0)
Service: `server/services/contracts.js` (`ctx.services.contracts`) · migration `058_contracts` (5 tables, BIGINT π on PostgreSQL) · UI in the `work` chunk · tests `server/test/contracts.test.js`, `tests/e2e/p78.e2e.test.js`.

- `POST /api/contracts` — client offer: `{to: handle | appId, title ≥ 6, scope ≥ 30, maxRevisions 0–5, milestones: 1–10 × {title, amount π (0 = unpaid), due, body}}`. From a job application only by its employer and only when the application is «offered» or «hired» (one open contract per application). Blocked pairs → 404. Paid contracts (any milestone > 0) are refused when either side is a minor (403 `minor_restricted`); unpaid contracts are allowed. `CONTRACT_MAX_OPEN` (25).
- `GET /api/contracts/draft?app=` — prefill from an application (worker, title, bid, days, ready). `GET /api/contracts` — `{open, closed}` for the member (as client or worker).
- `GET /api/contracts/:id` — contract, milestones with deliverables and the actions the viewer may take, timeline, disputes, Pi notice. Parties and staff only.
- `POST /api/contracts/:id/respond {accept, note}` (worker; accepting an offer from an «offered» application marks it hired) · `POST …/withdraw` (client, pending offer) · `POST …/cancel {note}` (client only while no money is held; the worker may always end it — held, undisputed milestones are refunded) · `POST …/messages` (risky messages warn the recipient).
- Milestones: `POST /api/contract-milestones/:id/fund` (client; Pi intent purpose `contract`; **501 `not_configured`** while Pi payments are off) → on `PI_PAYMENT_COMPLETED`: journal `user:<client>:pi_out` → `escrow:contracts`. `POST …/submit {note, links ≤ 5 http(s)}` (worker; paid milestones only once funded). `POST …/review {action: approve | revision, note}` (client; revisions up to the agreed number). Approval of a paid milestone: `escrow:contracts` → `work:<worker>:earnings` minus `CONTRACT_FEE_PCT` (default 0) to `platform:fees`. A submission left unreviewed for `CONTRACT_AUTO_RELEASE_DAYS` (14) is approved by the hourly sweep.
- Disputes: `POST /api/contract-milestones/:id/dispute {reason, body}` on a funded milestone (frozen). Staff: `GET /api/admin/contracts` (open disputes with deliverables, totals incl. escrow balance), `POST /api/admin/contract-disputes/:id {outcome: release | refund | split, workerShare, note}` — audited, both sides notified.
- A contract whose milestones are all done becomes `completed` when at least one was approved / paid out (otherwise `cancelled`); `completedFor(uid)` feeds phase 80 reviews.
- Finance (phase 60) counts `work:<id>:earnings` as a member balance («أرباحك من العقود») and `escrow:contracts` as escrow; ledger purpose `contract`.
- Notifications: `contract_offer`, `contract_status`, `contract_funded`, `contract_submitted`, `contract_review`, `contract_msg`, `contract_dispute`, `contract_resolved`. Data map: 4 entries (kept on erasure — shared financial records).
- UI: #/contracts[?tab=closed], #/contracts/new[?app=|to=], #/contract/:id, #/admin/contracts. Entry points: Settings → الحساب «العقود», «العقود» on #/jobs, «إنشاء عقد بمراحل» on an offered / hired application.

## Phase 79 — teams & group projects (v2.45.0)
Service: `server/services/teams.js` (`ctx.services.teams`) · migration `059_teams` (6 tables `wt_teams`, `wt_members`, `wt_invites`, `wt_tasks`, `wt_items`, `wt_updates`) · lazy UI chunk `teams` (`teams-ui.js`, `teams.css`) · tests `server/test/teams.test.js`, `tests/e2e/p79.e2e.test.js`.

- Kinds: team «فريق» or project «مشروع»; visibility private (invite only) or listed in the public directory. Roles: owner (one, transferable via `POST /api/teams/:id/transfer`), admin (invites, removes, edits), member (tasks, files, updates), viewer (reads, replies). Owners complete / archive / reopen (`POST /api/teams/:id/state`); staff can archive any team. `WT_MAX_MEMBERS` (50), `WT_MAX_OWNED` (20).
- `GET|POST /api/teams` (mine + pending invites) · `GET /api/teams/directory` (listed, Arabic-normalised search) · `GET|PATCH /api/teams/:id` (outsiders of a listed team see the card and may request to join).
- Joining: direct invite `POST /api/teams/:id/invites {handle, role, note}` → `POST /api/team-invites/:id/respond`; invite link `POST /api/teams/:id/invites {link: true, days 1–30, maxUses}` → `GET /api/teams/join/:code` + `POST /api/teams/join {code}`; revoke `POST /api/teams/:id/invites/:iid/revoke`; join request `POST /api/teams/:id/request` → `POST /api/teams/:id/requests/:iid {accept}`. Blocked pairs cannot invite each other. Members: `PUT /api/teams/:id/me` (title / leave), `PATCH|DELETE /api/teams/:id/members/:uid`.
- Task board: `POST /api/teams/:id/tasks`, `PATCH|DELETE /api/team-tasks/:id` — columns todo → doing → review → done, assignee (member), due date, priority, order, optional milestone of the linked contract.
- Files & links: `POST /api/teams/:id/items` (http(s) link or an uploaded image via the existing media upload), `DELETE /api/team-items/:id`.
- Updates & discussion: `POST /api/teams/:id/updates {kind: update | question, body, parent}`, `DELETE /api/team-updates/:id`; risky text (fees, off-platform payment, passphrase) is flagged for readers.
- Contracts (phase 78): `POST|PATCH /api/teams {contractId}` links a contract the owner is party to; the team shows its milestones and the contract page links back for members. A team linked to a paid contract does not take minors (and cannot be linked while it has one).
- Minors (phase 35): may join private teams by invite; cannot create listed teams, use links to / request listed teams, or join teams linked to paid contracts (403 `minor_restricted`).
- `completedFor(uid)` (completed teams the member belonged to) feeds phase 80 reviews.
- Notifications: `team_invite`, `team_joined`, `team_declined`, `team_request`, `team_removed`, `team_owner`, `team_task`, `team_update`. Data map: 6 entries (owned teams and created tasks kept on erasure as shared work; memberships, invites, items and updates deleted).
- UI: #/teams[?tab=directory|invites], #/teams/new, #/team/:id (board · members · files · updates), #/teams/join/:code. Entry points: Settings → الحساب «الفرق والمشاريع», «الفرق» on #/jobs and the contract page.

## Phase 80 — professional reputation & verified reviews (v2.46.0)
Service: `server/services/proreviews.js` (`ctx.services.proreviews`; the phase 7 `reputation.js` is the community trust score and is untouched) · migration `060_proreviews` (4 tables `pr_reviews`, `pr_endorsements`, `pr_reports`, `pr_prompts`) · lazy UI chunk `proreviews` (`proreviews-ui.js`, `proreviews.css`, loads after `work`) · tests `server/test/proreviews.test.js`, `tests/e2e/p80.e2e.test.js`.

- **Verified engagements only**: `contracts.completedFor(uid)` (both parties) and `teams.completedFor(uid)` (members other than viewers who were in the team ≥ `PR_TEAM_MIN_DAYS` (3) days before it was completed, with ≥ 1 finished task). Review window `PR_WINDOW_DAYS` (30) from completion.
- `GET /api/proreviews` — `{pending (engagement, role, criteria, deadline, theyReviewed), given, received, waiting, summary, windowDays}`.
- `POST /api/proreviews {kind: contract | team, ref, to: userId, overall 1–5, c1–c3 1–5 (optional), body 10–1500 (optional), skills[] (endorse while reviewing)}` → 403 `self_review` / `not_eligible`, 409 `window_closed` / `already_reviewed` (unique per engagement + author + reviewee), 404 for blocked pairs. Criteria by the author's role: client → worker «جودة العمل، التواصل، الالتزام بالمواعيد»; worker → client «وضوح المتطلبات، التواصل، سرعة المراجعة والاعتماد»; teammate «جودة المساهمة، التعاون والتواصل، الالتزام بالمواعيد». Risky text (fees, off-platform, passphrase, contact details) is flagged for readers.
- **Double-blind**: a review is revealed when the reverse review exists or at the window end (hourly sweep, also enforced on read). `PATCH /api/proreviews/:id` (author, until revealed). `PUT /api/proreviews/:id/response {body | null}` (reviewee, once revealed; no off-platform contact).
- **Aggregate** (`summaryOf`): average of *counted* reviews — published + revealed, the latest per author → reviewee pair only, not from accounts younger than `PR_MIN_ACCOUNT_DAYS` (7) or engagements shorter than `PR_MIN_ENGAGEMENT_HOURS` (24) (stored in `flags`, shown as «لا يُحتسب»). Also distribution, averages per role (as worker / client / teammate) and criterion, completed contracts + teams, endorsements, badges (first job, active 5+, trusted 20+ @ 4.5, top rated 4.7 over 5, on time 4.5 over 3 as worker, team player 3 teams, verified skills 3+ endorsements).
- **Where it shows**: `proprofile.build` adds `reputation` (so the CV, the employer's view of an application and the preview follow CV visibility); talent search rows and the employer pipeline add `rep` (avg, count, completed, 2 badges). `GET /api/proreviews/u/:handle` — the full page: blocked → 404; minors only to themselves, followers and staff; otherwise the CV visibility (members only when there is no CV).
- **Endorsements**: `GET|PUT /api/proreviews/endorse/:handle {skills[]}` — verified collaborators only (`not_collaborator`), skills on the member's professional profile only, up to `PR_ENDORSE_MAX` (5), replace / withdraw with `[]`.
- **Reports & staff**: `POST /api/proreviews/:id/report {reason: fake | abusive | private | offtopic | other, note}` (not the author; one per member) → `PR_FLAG_REPORTS` (3) open reports flag it (off the public page). `GET /api/admin/proreviews` (queue + reciprocal pairs with 2+ mutual engagements + totals), `POST /api/admin/proreviews/:id {action: dismiss | hide (note required) | restore}` — audited (`proreview_*`), author notified.
- Sweep (hourly, `sweep()`): one `prr_open` «you can review now» per engagement and member (`pr_prompts`), reveal at window end with `prr_received`.
- Notifications: `prr_open`, `prr_waiting`, `prr_received`, `prr_response`, `prr_endorsed`, `prr_moderated`. Data map: 4 entries (deleted on erasure).
- UI: #/reviews[?tab=pending|received|given], #/reviews/new?kind=&ref=&to= | ?edit=, #/reviews/u/:handle, #/admin/reviews. Entry points: Settings → الحساب «التقييمات المهنية», the reputation strip on #/cv/:handle, ratings on #/talent cards and job applicants, «قيّم التعامل» on completed contracts, «قيّم زملاءك» on completed teams.
